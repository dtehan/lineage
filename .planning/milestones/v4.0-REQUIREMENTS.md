# Requirements: Lineage v4.0

**Defined:** 2026-02-20
**Core Value:** Enable accurate impact analysis for database changes by visualizing complete column-level lineage across Teradata databases.

## v4.0 Requirements

Requirements for v4.0 First-Time Load Performance. Each maps to roadmap phases.

### In-Memory Graph Engine

- [x] **GRAPH-01**: Application loads all active OL_COLUMN_LINEAGE rows into a networkx DiGraph at startup
- [x] **GRAPH-02**: BFS traversal returns upstream lineage for a given column within <100ms (warm graph)
- [x] **GRAPH-03**: BFS traversal returns downstream lineage for a given column within <100ms (warm graph)
- [x] **GRAPH-04**: Bidirectional traversal returns both upstream and downstream lineage within <100ms (warm graph)
- [x] **GRAPH-05**: Graph engine falls back to existing CTE queries if in-memory graph is unavailable or loading
- [x] **GRAPH-06**: Graph rebuilds use blue-green swap pattern (build new graph, atomically swap reference) with no downtime
- [x] **GRAPH-07**: Background warm-up thread initializes graph during app startup without blocking request handling
- [x] **GRAPH-08**: BFS traversal produces semantically identical results to existing CTE queries (same nodes, edges, transformation types)

### Progressive Depth Loading

- [x] **PROG-01**: User sees depth-1 lineage graph rendered within 200ms of clicking a column
- [x] **PROG-02**: Full-depth lineage graph expands from depth-1 view via a second background query
- [x] **PROG-03**: Graph layout runs only on the final depth slice to prevent layout jitter
- [x] **PROG-04**: Existing graph nodes remain stable (no position jumping) when deeper levels are added
- [x] **PROG-05**: Loading progress indicator shows depth-1 complete, then full-depth expanding

### Cache Integration

- [x] **CACHE-01**: Existing /cache/invalidate endpoint also triggers in-memory graph rebuild
- [x] **CACHE-02**: Three-layer invalidation verified end-to-end: ETL trigger clears Redis cache AND rebuilds in-memory graph
- [x] **CACHE-03**: Graph engine serves CTE fallback during rebuild gap (no stale data served from old graph)

### Observability

- [x] **OBS-01**: API responses include timing headers showing database query time vs in-memory traversal time
- [x] **OBS-02**: Graph engine exposes metrics endpoint (node count, edge count, last rebuild time, memory usage)
- [x] **OBS-03**: Frontend loading progress displays per-stage timing (fetch, layout, render)

### Redis Serialization

- [x] **REDIS-01**: In-memory graph is serialized to Redis after successful warm-up
- [x] **REDIS-02**: On cold restart, graph restores from Redis serialization before falling back to Teradata query
- [x] **REDIS-03**: Redis-restored graph serves requests within <1s of app restart

## Out of Scope

| Feature | Reason |
|---------|--------|
| SSE streaming endpoint | Incompatible with sync Gunicorn workers; polling achieves same UX with zero infrastructure risk |
| Multi-worker shared graph | Single-worker + threads sufficient for current deployment; adds Redis Pub/Sub complexity |
| Canvas-based rendering | React Flow handles 200-node graphs fine; canvas rewrite only needed at 1000+ nodes |
| Data normalization (TRIM removal) | Low impact vs in-memory engine; can be done independently later |
| networkx → plain dict migration | Chose networkx for maintainability; optimize only if memory becomes an issue in production |
