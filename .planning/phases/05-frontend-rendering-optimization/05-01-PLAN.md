<objective>
Move ELKjs graph layout computation from the main thread to a Web Worker using Comlink for type-safe communication.

Purpose: The primary performance bottleneck is synchronous ELKjs layout on the main thread (LineageGraph.tsx lines 197-218), which freezes the UI for 3-5 seconds on large graphs. Moving this to a Web Worker allows the main thread to remain responsive during layout computation.

Output: Web Worker infrastructure for layout, useLayoutWorker hook, updated LineageGraph.tsx to use Worker-based layout.
</objective>

   - Create a module-level singleton Worker instance (NOT inside the hook — see pitfall in research):
     ```typescript
     const workerInstance = new Worker(
       new URL('../../../../workers/layout.worker.ts', import.meta.url),
       { type: 'module' }
     );
     ```
   - Wrap with Comlink: `const workerApi = wrap<LayoutWorkerAPI>(workerInstance);`
   - Export `useLayoutWorker` hook that returns `{ layoutGraph }` where `layoutGraph` is a `useCallback`-wrapped async function calling `workerApi.layout(rawNodes, rawEdges, options)`
   - Include error handling: wrap the Worker call in try/catch, log errors with `console.error`, and re-throw so the caller can handle it
   - The Worker singleton means only ONE Worker thread exists for the lifetime of the app — this is correct per research recommendation (single Worker, not pool)

2. Update `lineage-ui/src/components/domain/LineageGraph/hooks/index.ts`:
   - Add `export { useLayoutWorker } from './useLayoutWorker';` to the barrel file

3. Update `lineage-ui/src/components/domain/LineageGraph/LineageGraph.tsx`:
   - Import `useLayoutWorker` from `./hooks`
   - In `LineageGraphInner`, add: `const { layoutGraph: workerLayoutGraph } = useLayoutWorker();`
   - In the `useEffect` that handles data changes (around line 187-220), replace the direct `layoutGraph()` call with `workerLayoutGraph()`:
     - Before: `layoutGraph(legacyNodes, legacyEdges, { onProgress: ... })`
     - After: `workerLayoutGraph(legacyNodes, legacyEdges, {})`
     - Note: The `onProgress` callback CANNOT be passed to the Worker (functions are not serializable via structured clone). Instead, set progress manually:
       - Before calling Worker: `setProgress(35)` (entering layout)
       - After Worker returns: `setProgress(70)` (layout complete)
     - The `.then()` chain stays the same (setStage, setNodes, setEdges, setGraph, requestAnimationFrame)
     - The `.catch()` chain stays the same (console.error, fallback setGraph, setStage complete)
   - Remove the direct import of `layoutGraph` from `../../../utils/graph/layoutEngine` at the top of the file (it's now used via the Worker hook)
   - Keep the `convertOpenLineageGraph` import — that stays on the main thread (it's fast data transformation, not CPU-intensive layout)

Important edge case: The existing `layoutEngine.ts` `layoutGraph` function collects metrics (`collectMetrics` flag). These metrics will still be collected inside the Worker (they use `performance.now()` which is available in Workers). The metrics will be returned as part of `LayoutResult` through Comlink's structured clone. No changes needed for metrics.

Important: The Worker handles the `onProgress` callback removal gracefully because `LayoutOptions.onProgress` is optional (`onProgress?: (progress: number) => void`). Passing `{}` as options means no progress callback, which is fine — the Worker just skips those calls.
