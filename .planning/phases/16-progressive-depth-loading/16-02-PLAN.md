**Part B: Modify LineageGraph.tsx** — Replace the column lineage query with `useProgressiveLineage`. The critical change is that `data` returns depth-1 data as soon as it's available (not waiting for full-depth), so the layout effect fires on depth-1 and the spinner dismisses.

Step-by-step changes:

1. **Update imports** — Add `useProgressiveLineage` to the import from `useOpenLineage`. Remove `useOpenLineageGraph` import (it is only used for column lineage; table lineage uses `useOpenLineageTableLineage` which stays). Import `ProgressBanner`.

2. **Replace columnQuery** — Currently:
   ```typescript
   const columnQuery = useOpenLineageGraph(
     datasetId, fieldName, direction, maxDepth,
     { enabled: !isTableView && !!datasetId && !!fieldName }
   );
   ```
   Replace with:
   ```typescript
   const {
     depth1Query,
     fullDepthQuery,
     isDepth1Ready,
     isFullDepthReady,
     finalData: columnFinalData,
     isLoading: columnIsLoading,
     isFetchingFullDepth,
     error: columnError,
   } = useProgressiveLineage(datasetId, fieldName, direction, maxDepth, {
     enabled: !isTableView && !!datasetId && !!fieldName,
   });
   ```

3. **Unify data/isLoading/error — THIS IS THE CRITICAL FIX** — Replace the existing unified destructuring:
   ```typescript
   const { data, isLoading, isFetching, error } = isTableView ? tableQuery : columnQuery;
   ```
   With:
   ```typescript
   // For column lineage, `data` is depth-1 data when available (NOT waiting for full-depth).
   // This ensures the layout effect fires on depth-1 data, the spinner dismisses,
   // and the user sees the graph immediately. When full-depth arrives, `data` updates
   // to the full dataset and the layout effect re-fires.
   const columnData = isFullDepthReady ? columnFinalData : (isDepth1Ready ? depth1Query.data : null);
   const data = isTableView ? tableQuery.data : columnData;
   const isLoading = isTableView ? tableQuery.isLoading : columnIsLoading;
   const isFetching = isTableView ? tableQuery.isFetching : (depth1Query.isFetching || fullDepthQuery.isFetching);
   const error = isTableView ? tableQuery.error : columnError;
   ```

   **Why `columnData` returns depth-1 data early:** The existing plan had `data = columnFinalData` which is `null` until full-depth resolves. This meant:
   - `data?.graph` was falsy after depth-1 resolved, so the layout `useEffect` never fired
   - `stage` stayed at `'fetching'` (nothing reset or advanced it)
   - `showProgress` stayed `true` (because `stage !== 'idle' && stage !== 'complete'`)
   - The full-screen spinner remained, hiding the depth-1 graph entirely

   The fix: `columnData` returns `depth1Query.data` as soon as depth-1 resolves. This causes:
   - `data?.graph` to become truthy → layout effect fires on depth-1 data
   - `stage` advances through `layout → rendering → complete`
   - `showProgress` becomes `false` → spinner dismissed → graph visible
   - When full-depth resolves, `columnData` switches to `columnFinalData` → `data` changes → layout effect re-fires on full dataset

4. **The layout `useEffect` fires twice — this is intentional** — The existing `useEffect` that watches `data` and calls `layoutGraph` already works correctly for this pattern:
   - **First fire:** When depth-1 data arrives, `data?.graph` becomes truthy. Layout runs on depth-1 nodes. `stage` advances to `complete`. Graph is displayed.
   - **Second fire:** When full-depth data arrives, `data` changes (React detects reference change). The effect's cleanup function runs first (sets `cancelled = true`, calls `reset()`). Then the effect re-runs with full-depth data. Layout runs again on the full node set. `stage` advances to `complete` again.

   The `cancelled` flag in the existing effect already handles the transition safely — it prevents stale layout promises from the first run from corrupting state when the second run starts.

   No changes needed to this effect.

5. **Fix the showProgress/stage state machine** — The existing `showProgress` logic at line 594:
   ```typescript
   const showProgress = isLoading || (stage !== 'idle' && stage !== 'complete');
   ```
   This works correctly WITH the `columnData` fix because:
   - During depth-1 fetch: `isLoading = true` → `showProgress = true` → full-screen spinner
   - After depth-1 resolves: `isLoading = false`, AND `data?.graph` is truthy (because `columnData = depth1Query.data`), so the layout effect fires and advances `stage` to `layout → rendering → complete`. Once `stage = 'complete'`, `showProgress = false` → spinner dismissed.
   - During full-depth fetch: The layout effect's cleanup resets `stage` to `idle`. But `data` is immediately available with the new full-depth value, so the effect re-fires in the same render cycle, setting `stage = 'layout'`. However, `showProgress` is computed before effects run, so in the render where full-depth arrives: `isLoading = false` and stage is still whatever it was from the completion of depth-1 layout (either `complete` or being reset). Either way, the `showProgress` does NOT re-activate the full-screen spinner because `isLoading` remains `false` (depth-1 is done) and the effect will quickly advance stage through to `complete`.

   **However, there is a brief window:** When the cleanup from the layout effect calls `reset()` (setting stage to `idle`), and the new effect hasn't set `stage = 'layout'` yet, a render COULD see `stage = 'idle'` and `isLoading = false`, resulting in `showProgress = false`. This is actually fine — we WANT the spinner to stay dismissed during the full-depth transition. The graph from depth-1 remains visible while the ProgressBanner shows.

   No changes needed to the `showProgress` expression.

6. **Render ProgressBanner** — Add between the Toolbar and the graph/table view section (inside the Profiler return, after the LargeGraphWarning). This is BELOW the `if (showProgress)` early return, so it's only reachable when the spinner is dismissed (i.e., depth-1 has been rendered):
   ```tsx

     message="Expanding to full depth..."
     visible={!isTableView && isFetchingFullDepth}
   />
   ```

7. **Update handleRefresh** — The refresh function currently uses `queryClient.setQueryData` with specific query keys. For column lineage, it should invalidate both the depth-1 and full-depth query keys. Replace the column lineage branch:
   ```typescript
   } else {
     const freshData = await openLineageApi.getLineageGraph(datasetId, fieldName, {
       direction,

       refresh: true,
     });
     // Invalidate both depth-1 and full-depth cache entries

   }
   ```

**Position stability note (PROG-04):** Layout runs twice (once on depth-1, once on full-depth). The layout engine uses a deterministic topological layout algorithm (O(V+E), completes in <10ms). When full-depth data adds new nodes:
- Nodes in the same layers as depth-1 nodes maintain their layer assignment (longest-path layering is deterministic).
- New nodes may shift existing nodes in the secondary axis (vertical stacking within a layer).
- This position shift is acceptable because: (a) the layout is near-instant (<10ms), so the transition is not perceptible as "jumping" — it appears as a smooth graph expansion; (b) the full-depth data typically adds nodes in deeper layers (farther from the root), not between existing nodes.

If position jumping proves to be a UX issue in practice, a follow-up can record depth-1 node positions and pin them as constraints for the second layout run. But the deterministic topological layout makes this unlikely to be noticeable.

**Important anti-patterns to avoid:**
- Do NOT make `data = columnFinalData` (null until full-depth). This is the original bug — it hides the depth-1 graph behind the spinner.
- Do NOT add new LoadingStage values to useLoadingProgress. The existing stages handle both layout passes.
- Do NOT change the table-level lineage path. `isTableView` branch is untouched.
- Do NOT try to prevent the layout from running twice. Two fast layouts (<10ms each) are better than waiting for full-depth with a spinner.
