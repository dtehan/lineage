**Part B: Modify LineageGraph.tsx** — Replace the column lineage query with `useProgressiveLineage` and gate the layout effect on `finalData`.

Step-by-step changes:

1. **Update imports** — Add `useProgressiveLineage` to the import from `useOpenLineage`. Remove `useOpenLineageGraph` import (it is only used for column lineage; table lineage uses `useOpenLineageTableLineage` which stays). Import `ProgressBanner`.

2. **Replace columnQuery** — Currently:
   ```typescript
   const columnQuery = useOpenLineageGraph(
     datasetId, fieldName, direction, maxDepth,
     { enabled: !isTableView && !!datasetId && !!fieldName }
   );
   ```
   Replace with:
   ```typescript
   const {
     depth1Query,
     fullDepthQuery,
     isDepth1Ready,
     isFullDepthReady,
     finalData: columnFinalData,
     isLoading: columnIsLoading,
     isFetchingFullDepth,
     error: columnError,
   } = useProgressiveLineage(datasetId, fieldName, direction, maxDepth, {
     enabled: !isTableView && !!datasetId && !!fieldName,
   });
   ```

3. **Unify data/isLoading/error** — Replace the existing unified destructuring:
   ```typescript
   const { data, isLoading, isFetching, error } = isTableView ? tableQuery : columnQuery;
   ```
   With:
   ```typescript
   const data = isTableView ? tableQuery.data : columnFinalData;
   const isLoading = isTableView ? tableQuery.isLoading : columnIsLoading;
   const isFetching = isTableView ? tableQuery.isFetching : (depth1Query.isFetching || fullDepthQuery.isFetching);
   const error = isTableView ? tableQuery.error : columnError;
   ```

   **Critical:** `data` for column lineage is now `columnFinalData` (full-depth when ready, else null). The layout effect already triggers on `data` changes, so it will fire only once — when `finalData` becomes non-null (after full-depth resolves, or after depth-1 resolves when maxDepth=1).

4. **Do NOT modify the layout useEffect** — The existing `useEffect` that watches `data` and calls `layoutGraph` already works correctly. It fires when `data` transitions from null/undefined to a value. Since `columnFinalData` starts as `null` and becomes non-null only when the final dataset is ready, the layout fires exactly once. No changes needed to this effect.

5. **Update showProgress logic** — The full-screen spinner should only show during the initial fetch (before depth-1 resolves). Once depth-1 is ready, the ProgressBanner handles the background fetch UX.
   ```typescript
   const showProgress = isLoading || (stage !== 'idle' && stage !== 'complete');
   ```
   This existing logic already works because `isLoading` for column lineage is `depth1Query.isLoading` (true only during depth-1 fetch). After depth-1 resolves and `data` (finalData) is still null (full-depth loading), the stage will still be idle or complete from the previous reset — the full-screen spinner does NOT re-appear because `isLoading` is false.

   **However**, there is a subtle issue: when depth-1 resolves but full-depth hasn't loaded yet, `data` (`columnFinalData`) is still `null`. The layout effect hasn't fired, so `stage` stays at whatever it was. We need to handle this:
   - When `isLoading` is true (depth-1 fetching), the full-screen spinner shows (existing behavior).
   - When `isLoading` is false and `data` is null (full-depth loading but depth-1 done), we do NOT show the full-screen spinner. Instead, the ProgressBanner shows.
   - When `data` is available (full-depth arrived), the layout fires and stages progress normally.

   The existing `showProgress` logic already handles this correctly because `isLoading = depth1Query.isLoading` becomes false when depth-1 resolves, and `stage` resets to idle between data loads.

6. **Render ProgressBanner** — Add between the Toolbar and the graph/table view section:
   ```tsx
   {/* Progressive depth loading banner */}
   <ProgressBanner
     message="Expanding to full depth..."
     visible={!isTableView && isFetchingFullDepth}
   />
   ```

7. **Update handleRefresh** — The refresh function currently uses `queryClient.setQueryData` with specific query keys. For column lineage, it should invalidate both the depth-1 and full-depth query keys. Replace the column lineage branch:
   ```typescript
   } else {
     const freshData = await openLineageApi.getLineageGraph(datasetId, fieldName, {
       direction,
       maxDepth,
       refresh: true,
     });
     // Invalidate both depth-1 and full-depth cache entries
     queryClient.setQueryData(
       ['openlineage', 'lineage', datasetId, fieldName, direction, maxDepth],
       freshData
     );
     // Also update depth-1 if maxDepth > 1 (depth-1 is a subset)
     if (maxDepth > 1) {
       queryClient.invalidateQueries({
         queryKey: ['openlineage', 'lineage', datasetId, fieldName, direction, 1],
       });
     }
   }
   ```

**Important anti-patterns to avoid:**
- Do NOT trigger ELK layout when depth-1 data arrives. The layout effect is gated on `data` which is `finalData` — this is the zero-jitter guarantee.
- Do NOT add new LoadingStage values to useLoadingProgress. The dynamic message override in `displayMessage` is sufficient.
- Do NOT change the table-level lineage path. `isTableView` branch is untouched.
