<objective>
Close the UAT gap: OL_COLUMN_LINEAGE has zero view-chain records, so upstream lineage through views is invisible. Implement automatic view lineage derivation that fetches view SQL definitions from `DBC.TablesV.RequestText`, parses them with SQLGlot to extract column-level source->target mappings, and inserts the results as OL_COLUMN_LINEAGE records.

Purpose: Without view lineage data, the lineage graph cannot show how data flows from source tables through views. Plan 10-01 added sourceType propagation so views render correctly, but the underlying lineage edges do not exist. This plan populates them automatically for any view registered in OL_DATASET.

Output: `view_lineage_extractor.py` module, `--views` flag on `populate_lineage.py`, unit tests, and populated OL_COLUMN_LINEAGE records for all discoverable views.
</objective>

**Core method `extract_all()`:**

1. **Discover views:** Query OL_DATASET for all rows where `source_type = 'VIEW'` and `is_active = 'Y'`. Return list of `(dataset_id, name)` tuples. The `name` is in format `DATABASE.VIEWNAME`.

2. **Fetch view definitions:** For each view, query `DBC.TablesV` for `RequestText` where `DatabaseName` and `TableName` match. Use the SAME batch pattern as `wildcard_resolver.py._fetch_view_definitions()` -- batch OR conditions, handle `RequestTxtOverFlow`, fallback to SHOW VIEW for truncated definitions. Process in batches of 100.

3. **Parse each view and extract lineage:**
   For each view with a valid definition:
   a. Normalize `REPLACE VIEW` to `CREATE VIEW` (Teradata stores definitions this way -- see `wildcard_resolver.py` line 468-475 for the regex pattern).
   b. Parse with `sqlglot.parse_one(sql, dialect="teradata")`, falling back to generic dialect on failure.
   c. Extract the SELECT expression from the CREATE VIEW AST (same pattern as `wildcard_resolver.py` lines 492-506: handle `exp.Create` -> `.expression` which may be `exp.Subquery` -> `.this` -> `exp.Select`).
   d. Build table alias map from the FROM/JOIN clauses: iterate over `select_expr.find_all(exp.Table)` and map alias -> (database, table). For unqualified tables, use the view's database as default.
   e. Extract column mappings from the SELECT clause's expressions:
      - For each `exp.Alias` or `exp.Column` in `select_expr.expressions`:
        - If it's `exp.Star` (SELECT *): look up columns from OL_DATASET_FIELD for the source table and create a 1:1 mapping by ordinal position to the view's fields (also from OL_DATASET_FIELD). Log a warning if column counts don't match.
        - If it's a qualified `exp.Column` (e.g., `t.col1`): resolve the table alias to get source_database.source_table, use column name as source_field. The target_field is the alias name if aliased, otherwise the column name.
        - If it's an unqualified `exp.Column`: try to resolve by checking which source table has that column (query OL_DATASET_FIELD). If ambiguous (multiple tables), skip with warning.
        - If it's an expression (e.g., `TRIM(a) || ' ' || TRIM(b) AS full_name`): walk the expression tree with `expr.find_all(exp.Column)` to find all source columns. Create a lineage record from each source column to the target (aliased) column with transformation_type `CALCULATION`.
   f. For each extracted mapping, build a lineage record dict with: source_dataset (database.table), source_field, target_dataset (view's database.viewname), target_field, transformation_type (DIRECT for simple column refs, CALCULATION for expressions), confidence_score (0.90 for direct, 0.80 for expressions, 0.70 for wildcard-expanded).

4. **Handle nested views:** After processing all views in a first pass, check if any source_dataset in the extracted lineage is itself a view (i.e., exists in the discovered views set). The lineage will naturally chain: if V2 selects from V1 which selects from T, the first pass creates T->V1 edges and V1->V2 edges. The recursive CTE in the lineage service already handles multi-hop traversal, so no special nesting logic is needed in the extractor -- just process all views.

5. **Insert lineage records:** Use the same INSERT pattern as `populate_lineage_from_fixtures()` in `populate_lineage.py`:
   - Generate `lineage_id` using `generate_ol_lineage_id(source_path, target_path)` from populate_lineage.py
   - Use `namespace_uri` for both `source_namespace` and `target_namespace`
   - Set `transformation_description` to `"Derived from view definition"`
   - Handle duplicate key errors gracefully (skip with no error, same as fixtures)
   - Return count of inserted records

6. **Logging:** Use Python's `logging` module with logger name `'view_lineage_extractor'`. Log:
   - INFO: number of views discovered, number of definitions fetched, number of lineage records inserted
   - WARNING: parse failures, truncated definitions, ambiguous columns, wildcard count mismatches
   - DEBUG: per-view extraction details

**Error handling:** If a view's definition cannot be fetched or parsed, log a warning and skip it. Never crash the whole extraction for one bad view. Wrap the per-view processing in try/except.
