<objective>
Extend WildcardResolver with view detection, definition retrieval, recursive expansion, and cache integration so that resolve_star() works transparently for both tables and views.

Purpose: When a query references a view containing SELECT *, the wildcard resolver must expand the view's definition to derive the actual column list. Without this, lineage through views is incomplete.

Output: Extended wildcard_resolver.py with 5 new methods: _identify_views(), _fetch_view_definitions(), _fetch_view_definition_show_view(), _expand_view_columns(), and _ViewExpansionProxy class. Modified warm_cache() to integrate view expansion before table metadata queries.
</objective>

Add 4 new methods and 1 helper class to WildcardResolver, plus new instance attributes:

**New class constant:**
- `MAX_VIEW_EXPANSION_DEPTH = 3` (separate from CTE's 5-level limit in TeradataSQLParser)

**New instance attributes in __init__():**
- `self._view_expansion_cache: Dict[Tuple[str, str], List[str]] = {}` — caches expanded view column lists
- `self._view_expansion_depth: int = 0` — tracks current recursion depth
- `self._view_expansion_path: Set[Tuple[str, str]] = set()` — tracks expansion path for cycle detection

**New imports needed:**
- `import re` (for REPLACE VIEW normalization)
- Add `sys` and `os` to support importing TeradataSQLParser from lineage-api/utils/

**Method 1: _identify_views(table_refs) -> Set[Tuple[str, str]]**
- Accept list of (database, table) tuples (already normalized)
- Build batch query: `SELECT TRIM(DatabaseName), TRIM(TableName) FROM DBC.TablesV WHERE (conditions) AND TableKind = 'V'`
- Use same OR-condition pattern as _warm_cache_batch() for batch query
- Apply same BATCH_SIZE (100) limit — split into multiple queries if needed
- Return set of (database, table) tuples that are views
- Log: `logger.debug(f"Identified {len(views)} views out of {len(table_refs)} table references")`
- Return empty set on error (graceful degradation, log warning)

**Method 2: _fetch_view_definitions(view_refs) -> Dict[Tuple[str, str], Optional[str]]**
- Accept set of (database, table) tuples that are views
- Try query with RequestTxtOverFlow column first:
  `SELECT TRIM(DatabaseName), TRIM(TableName), RequestText, RequestTxtOverFlow FROM DBC.TablesV WHERE (conditions) AND TableKind = 'V'`
- If RequestTxtOverFlow = 'Y': set definition to None (signal for SHOW VIEW fallback), log warning about truncation
- If no overflow: strip and store the RequestText
- On exception (column not available): fallback query without RequestTxtOverFlow
  - In fallback: if len(text) >= 12500, treat as truncated (set to None), log warning
- Pattern from dataset_repository.py lines 485-520
- Return dict mapping (database, table) -> view SQL string or None if truncated

**Method 3: _fetch_view_definition_show_view(database, table) -> Optional[str]**
- Execute `SHOW VIEW {database}.{table}` as fallback for truncated definitions
- Join all result rows with newline
- Return stripped text, or None on any exception
- Log warning on failure: `f"SHOW VIEW failed for {database}.{table}: {e}"`

**Method 4: _expand_view_columns(database, table, view_sql, all_view_definitions) -> List[str]**
- Check `_view_expansion_cache` first — return cached result if available
- Check depth limit: if `_view_expansion_depth >= MAX_VIEW_EXPANSION_DEPTH`, log warning, return []
- Check cycle: if `(database, table)` in `_view_expansion_path`, log ERROR with full path, return []
- Increment depth, add to path (use try/finally for cleanup)
- Normalize view SQL: `re.sub(r'^\s*REPLACE\s+VIEW', 'CREATE VIEW', view_sql, count=1, flags=re.IGNORECASE)` — Teradata stores as REPLACE VIEW in RequestText
- Parse with sqlglot: `sqlglot.parse_one(normalized_sql, dialect="teradata")`, fallback to `sqlglot.parse_one(normalized_sql)` on error
- Extract SELECT expression from parsed AST:
  - If isinstance(parsed, exp.Create): select_expr = parsed.expression; if Subquery, unwrap
  - If isinstance(parsed, exp.Select): use directly
- Create _ViewExpansionProxy instance with parent resolver reference and all_view_definitions
- Create fresh TeradataSQLParser instance: `TeradataSQLParser(default_database=database, wildcard_resolver=proxy)`
  - Import path: `sys.path.insert(0, os.path.join(os.path.dirname(__file__), '..', '..', '..', 'lineage-api'))` (only if not already in path)
  - `from utils.sql_parser import TeradataSQLParser`
- Call `parser._table_aliases = {}` then `parser._build_table_aliases(select_expr)` then `parser._extract_select_columns(select_expr)`
- Extract column names: `[ref.alias or ref.column for ref in col_refs if (ref.alias or ref.column)]`
- Cache result in `_view_expansion_cache` and `_column_cache`
- Log: `logger.info(f"Expanded view {database}.{table} -> {len(columns)} columns at depth {depth}")`
- Return columns list
- On any parse/extraction failure: log warning, return []

**Helper class: _ViewExpansionProxy**
- Implements resolve_star(database, table) interface (same as WildcardResolver)
- Constructor takes: parent_resolver (WildcardResolver), all_view_definitions dict
- resolve_star() logic:
  1. Check parent_resolver._column_cache for table columns (already cached tables)
  2. Check parent_resolver._view_expansion_cache for already-expanded views
  3. If (database, table) is in all_view_definitions and has SQL: call parent_resolver._expand_view_columns() recursively
  4. Otherwise return [] (graceful degradation)
- This avoids re-entering the database during nested expansion

**Do NOT use parameterized queries** — follow existing pattern in _warm_cache_batch() which builds SQL strings directly (DBC system views don't support parameterized queries consistently across Teradata versions).

Modify warm_cache() to integrate view expansion into the existing cache warming flow. The key insight: views should be detected and expanded BEFORE the DBC.ColumnsJQV batch query for regular tables.

**Modified warm_cache() flow (after normalization and deduplication):**

1. **Identify views** (new step): Call `_identify_views(unique_refs)` to get set of view references
2. **Separate tables from views**: `table_only_refs = [r for r in unique_refs if r not in view_refs]`
3. **Warm table cache** (existing): Process `table_only_refs` through existing batch loop with `_warm_cache_batch()`
4. **Fetch view definitions** (new step): Call `_fetch_view_definitions(view_refs)` for all views
5. **Handle truncated definitions** (new step): For views where definition is None (truncated), call `_fetch_view_definition_show_view(db, tbl)` as fallback
6. **Reset expansion state** (new step): Reset `_view_expansion_depth = 0`, `_view_expansion_path = set()`, `_view_expansion_cache = {}`
7. **Expand each view** (new step): For each view ref, call `_expand_view_columns()` to derive column list. If columns returned, store in `_column_cache[(db, tbl)] = columns`. Log warning if expansion yields no columns.
8. **Schema evolution detection** (existing, unchanged): If baseline_path, call `_detect_schema_changes()` and `_save_baseline()`

**Important implementation details:**
- If `_identify_views()` fails or returns empty set, fall through to existing behavior (all refs treated as tables, queried via ColumnsJQV). This preserves backward compatibility.
- The try/except around the entire warm_cache() body is already present — view expansion errors caught by existing graceful degradation.
- View expansion happens AFTER table cache is warmed (step 3), so that _ViewExpansionProxy can find base table columns when expanding views that reference tables.
- Log summary after view expansion: `logger.info(f"View expansion: {views_expanded}/{len(view_refs)} views expanded successfully")`

**Do NOT change the resolve_star() method** — it already looks up (database, table) from _column_cache. Once warm_cache() populates the cache with view-derived columns, resolve_star() works transparently.

**Do NOT change _detect_schema_changes() or _save_baseline()** — they already iterate _column_cache, which now includes both table and view entries. Schema evolution detection automatically covers views.
