- Create a helper method to configure mock cursor to respond differently based on query content (DBC.TablesV vs DBC.ColumnsJQV):
  ```python
  def _configure_cursor(self, view_rows=None, column_rows=None, request_text_rows=None):
      """Configure mock cursor to return different results based on query."""
      def mock_execute(query, *args):
          self._last_query = query
      self.mock_cursor.execute = mock_execute

      def mock_fetchall():
          if hasattr(self, '_last_query'):
              if 'TableKind' in self._last_query and 'RequestText' not in self._last_query:
                  return view_rows or []
              elif 'RequestText' in self._last_query:
                  return request_text_rows or []
              elif 'ColumnsJQV' in self._last_query:
                  return column_rows or []
          return []
      self.mock_cursor.fetchall = mock_fetchall
  ```

**Key insight:** These tests use MockWildcardResolver pre-populated with view-derived column lists. Since resolve_star() is the interface between the parser and the resolver, we simulate view expansion by providing the view's column list directly in the mock resolver's column_map.

**Test class: TestViewExpansion(unittest.TestCase)**

- SQL: `INSERT INTO demo_user.target (id, full_name, contact) SELECT * FROM demo_user.customer_view`
- Assert 3 lineage records with correct ordinal matching
- Assert confidence = 0.70 (wildcard expansion)
- This verifies the end-to-end flow: view columns in resolver -> parser expands SELECT * -> correct lineage

**Test 2: test_ctas_select_star_from_view**
- Configure MockWildcardResolver with view columns: `('demo_user', 'order_view'): ['order_id', 'amount', 'status']`
- SQL: `CREATE TABLE demo_user.new_orders AS (SELECT * FROM demo_user.order_view) WITH DATA`
- Assert 3 lineage records with target columns derived from source (order_id, amount, status)

**Test 3: test_qualified_wildcard_from_view**
- Configure MockWildcardResolver with view AND table columns:
  `('demo_user', 'customer_view'): ['customer_id', 'name']` and `('demo_user', 'orders'): ['order_id', 'amount']`
- SQL: `INSERT INTO demo_user.target (a, b, c, d) SELECT cv.*, o.* FROM demo_user.customer_view cv JOIN demo_user.orders o ON cv.customer_id = o.order_id`
- Assert 4 lineage records: customer_id->a, name->b, order_id->c, amount->d
- This verifies qualified wildcards work with views (not just tables)

**Test 4: test_view_with_explicit_columns_mixed**
- Configure MockWildcardResolver with: `('demo_user', 'my_view'): ['col1', 'col2']`
- SQL: `INSERT INTO demo_user.target (a, b, c) SELECT v.*, v.col1 AS extra FROM demo_user.my_view v`
- Assert lineage includes both wildcard-expanded and explicit columns
- Wildcard columns get 0.70 confidence, explicit column gets 0.95

**Test 5: test_view_no_columns_graceful_degradation**
- Configure MockWildcardResolver with empty view: `('demo_user', 'empty_view'): []`
- SQL: `INSERT INTO demo_user.target (a) SELECT * FROM demo_user.empty_view`
- Assert no crash, lineage is an empty list or falls back to pattern-based

**Test 6: test_view_columns_through_subquery**

- This verifies nested subquery + view combination works
